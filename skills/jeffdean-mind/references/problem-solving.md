# 문제 해결 접근법

## Dean의 3단계 문제 해결

### 1. First-principles로 다시 생각하기
> "문제를 오늘날 정확히 어떻게 풀리는지에 얽매이지 말고, 첫 원리로 어떻게 풀지
> 생각하면, 다른 사람들이 생각하지 못한 정말 좋은 아이디어를 낼 수 있다."

적용: 기존 해법을 조사하되, 그것을 출발점이 아닌 비교 대상으로 삼는다.
"이 문제의 물리적 하한은 무엇인가? (데이터 크기 ÷ 대역폭, 왕복 횟수 × RTT)"부터
계산하고, 기존 해법이 하한에서 얼마나 먼지 본다.

### 2. 작은 규모에서 대량 실험 → 유망한 것만 스케일업
> "1/1000 규모 문제를 두고 10만 개 아이디어를 검증한 다음, 유망해 보이는 것만
> 스케일업하는 게 매우 유용하다."

- 실험은 **"2주가 아니라 1~2시간"** 걸리게 설계한다. 실험 사이클 타임 자체가
  설계 대상이다.
- 축소 버전(데이터 1/1000, 모델 1/100)에서 아이디어를 거르고, 통과한 것만
  전체 규모로 올린다.

### 3. 조합 시 상호작용 검증
개별로 좋았던 개선들이 합쳤을 때 나쁘게 상호작용할 수 있다.
- 주기적으로 개선들을 함께 묶어 검증한다.
- 조합이 안 맞으면 넘어가지 말고 **원인을 이해**한다.

## 마이크로벤치마크와 프로파일링 습관

> "마이크로벤치마크를 작성하라! 성능을 이해하는 데 훌륭하고, 백오브엔벨로프 계산의
> 직관을 길러주며, 성능 개선 테스트의 사이클 타임을 줄인다."

운영 시스템에는 다음을 기본 내장 (Dean이 구글 서버 전체에 요구한 것):
- HTML 상태 페이지
- 키-값 모니터링 인터페이스
- 저오버헤드 온라인 프로파일링 (CPU/메모리/락 경합)

> "시스템이 느리거나 오작동할 때, 그 이유를 알아낼 수 있는가?"

이 질문에 "아니오"면 관측 도구부터 만든다.

## 데이터 인코딩 철학

원칙: **"CPU는 빠르고 메모리/대역폭은 귀하다."**

- 가변 길이 인코딩(varint), 압축, 컴팩트한 인메모리 표현을 기본 고려.
- 트레이드오프는 항상 수치로 저울질:
  - Zippy: 인코딩 300MB/s, 디코딩 600MB/s, 압축률 2–4배
  - gzip: 인코딩 25MB/s, 디코딩 200MB/s, 압축률 4–6배
  - → 처리량이 병목이면 Zippy, 저장 비용이 병목이면 gzip.

## 성능 강박의 뿌리 (태도)

- Dean: "나는 항상 빠르게 도는 코드를 좋아했다 (I've always liked code that runs
  fast)." 고교 시절 역학조사 소프트웨어 Epi Info를 만들며 당시 전문가용 도구보다
  "26배 빠르다"고 스스로 측정해 밝혔다 — **개선 주장은 항상 배수(倍數)로 정량화**하는
  습관은 이때부터다. (Epi Info는 CDC에 채택되어 13개 언어로 번역됐다.)
- Ghemawat이 본 Dean: "그는 코드를 쓰는 동안 머릿속에 모델이 돌아간다 — '이 코드의
  성능은 어떻게 될까?' 그는 거의 반자동으로 모든 코너 케이스를 생각한다."
- 컴파일러 최적화 박사 출신(워싱턴 대학, Craig Chambers 지도, 1996, 논문
  "Whole-Program Optimization of Object-Oriented Languages")의 "기계에 매우 가까운
  (very close to the machine)" 사고 — 코드 한 줄이 캐시·분기 예측·메모리 계층에서
  어떻게 실행되는지 상상하며 쓴다.
